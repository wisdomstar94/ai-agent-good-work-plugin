지정한 코드 변경 내용을 **리뷰**하고 **HTML 리뷰 결과서**를 만드세요.

사용자가 넘긴 인자는 **대상 브랜치 · PR 번호** 또는 **커밋 범위**로 해석하세요 : `$ARGUMENTS`

`$ARGUMENTS` 가 비어 있거나 치환되지 않은 글자 그대로 보이면, 사용자의 요청 문장에서 범위를 찾으세요.

사용자가 범위를 제한하지 않았으면 **기본 브랜치(main 등) 대비 현재 브랜치의 변경사항**(커밋된 변경과 커밋하지 않은 작업 트리 변경 모두)을 대상으로 합니다.

---

## 코드 리뷰

- 변경된 내용을 파악해서 정리합니다.
- 변경으로 인해 사이드이펙트가 **발생할 여지가 있는 곳**과 **발생이 확실한 곳**을 파악하고, 우려되는 점도 전부 나열합니다.
- 변경된 코드와 그 주변 코드에서, 현재 코드와 맞지 않는 낡은 주석이 있는지 확인합니다.
- 추가 · 변경된 파일의 위치가 `code-splitting-skill` 스킬(이 스킬 폴더 기준 `../code-splitting-skill/SKILL.md`)의 `코드는 사용처 가까이에 두세요` 기준에 맞는지 확인합니다.
  - 공용 폴더에 있는 코드가 실제로는 한 곳에서만 쓰이면 사용처 옆 그룹핑 폴더로 옮기라고 지적합니다.
  - 그룹핑 폴더 밑 코드를 다른 사용처에서 끌어다 쓰고 있으면 공용 폴더로 옮기라고 지적합니다.
- 리뷰에서 지적한 내용에 대한 해결책을 같이 제안합니다.

## HTML 리뷰 결과서 작성

- 코드 리뷰 내용은 워크스페이스 루트 기준 `./logs/코드리뷰결과서/YYYYMM/YYYYMMDD/YYYYMMDD_HHmmss_작업설명_코드리뷰결과서.html` 경로에 단일 HTML 파일로 생성하세요.
- `html-writing-skill` 스킬의 HTML 형식 규격(이 스킬 폴더 기준 `../html-writing-skill/SKILL.md`)을 준수하세요.

## 금지 사항

- 리뷰를 하면서 코드를 임의로 수정하지 마세요. 수정이 필요한 부분은 HTML 리뷰 결과서에 포함하여 사용자가 한 번에 확인할 수 있게 하세요.
